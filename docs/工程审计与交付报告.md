# QueryStep 工程审计与交付报告

更新日期：2026-11-20。本报告描述当前实现与本轮实测，替代 2026-11-10 的训练准备阶段结论。范围是受控 SQL 教学试点，不是已完成公网生产验收的商业产品。

## 1. 交付结论与定位

QueryStep 已从“知识追踪选题 + 对话接口”扩展为证据驱动的 SQL 学习工作台：正式 EpiKT 负责已映射题目的候选评分，学生可以另行编写 SQL，由受限执行器查找具体反例，动态教练再选择检查、检索和追问。程序判分、LLM 建议与学习者确认的记录各有独立边界。

适合展示的工程价值是：研究模型的可靠落地、可回放的学习上下文、受权限约束的工具编排、可取消恢复的长任务，以及具有失败率与成本口径的评估。新增框架的数量不是交付指标；不能据此声称已经证明学习收益，或已经具备开放公网的安全与运维条件。

## 3. 模型与数据完整性

- 沿用随附 pyKT 的预处理、训练、题目窗口 `late_mean` 评估与四位小数口径。KC 放入 `q_data`、题号放入 `pid_data`；同一原题的多个 KC 使用相同的作答前历史。
- 在线窗口保留完整原题事件，正式模型权重未因本次功能开发而修改。实作任务不加入正式模型词表，不将帮助后的活动混入独立首答。
- 本轮真实验证在全新的合成会话完成三次正式答题后取得 EpiKT 推荐，实作教练收到同一历史版本的真实模型快照与四个已映射候选；运行结束后正式进度未变化。
- 既有正式离线结果不因为增加 Agent 而改变。EpiKT 相对强基线的收益应继续按原评估报告和置信区间解释，不能把新的 SQL 验证准确率当作知识追踪性能。

## 4. 运行与安全控制

### SQL 执行

SQLGlot AST 限定单条只读查询、表与函数；SQLite authorizer 再次约束访问。每次执行使用短生命周期子进程、内存数据库、空环境、关闭额外文件描述符，并设置时间、内存、指令、行数和响应大小限制。不会把提供方密钥环境传入查询进程。

这里只支持经过测试的 SQL 子集。CTE、递归查询、写操作、外部表、加载扩展等被拒绝。macOS/Linux 资源约束不是能抵抗解释器或 SQLite 原生漏洞的完整 OS 沙箱；公网仍需低权限容器或更强隔离。

### 教练与恢复

- 每轮最多 5 次模型调用、6 次工具调用、20 秒活动预算；单次模型 8 秒、工具 4 秒。MCP 冷启动另计入端到端耗时。
- 本轮沿用应用数据库内的结构化运行追踪，不额外部署外部追踪平台。课程检索方式与语料指纹写入运行事件并在界面显示，刷新/恢复后仍可追溯；不会把学生文本上传给独立追踪服务。
- 检查点保留已完成动作、真实用量、版本绑定和累计预算；恢复不会清空预算。题面、提示、模型或已确认笔记版本不兼容时拒绝恢复旧计划。
- 取消不仅改变页面状态，还按精确请求 ID 通知共享 MCP 服务端，再向正在执行的查询传递取消信号；其他并发请求保持独立。已取消结果不会被迟到响应覆盖。
- 反例优先于后续局部通过：模型不能通过只引用样本通过而隐藏已发现的错误。
- 严格校验不接受空引用的确定回答、虚构证据 ID、非原文课程引用、额外权限参数或新 SQL。模型异常时保留已取得证据并明确降级，不伪造成功。

### 数据与部署

匿名 Cookie 仅提供浏览器会话隔离，不是完整账户鉴权。当前有每会话活动任务和速率限制、排队阈值；重建匿名会话仍可绕过会话限流，因此不能宣传为公网全局防滥用。

数据库包含 SQL 文本、运行证据、草稿和学习笔记，属于学习数据。`.env`、API Key、真实学习者数据库、原始会话和新生成评估产物不提交到 Git。备份应包含 `sql_drafts` 与 `sql_runs`；当前采用启动建表，尚非完整版本化数据库迁移体系。

## 5. 可重复验证

### 自动与浏览器回归

生产构建通过 TypeScript 和 Vite 检查。本轮最终完整 Python 回归 323 项通过，覆盖 SQL 拒绝边界、资源与取消控制、MCP 身份契约、规划引用、幂等/草稿冲突、版本恢复、令牌统计和原正式流程。

另在真实本地 API 用 8 个合成会话同时提交验证，8 个任务均完成，观察到最多 2 个运行中任务；相同幂等键返回原运行，跨会话读取返回 404。这是有限并发冒烟，不是生产容量或长期压测结果。

浏览器替身测试覆盖保存失败与冲突、跨任务状态、幂等重试、输入法、取消/恢复、状态读取失败、转义渲染、全部已定义错误码、正式页面状态保留、教练未配置及 320px 布局。替身模式拦截全部 API，不向用户运行中的后端转发。

真实浏览器使用独立 8001/5174 服务与合成数据库：`COUNT(*)` 在样本执行成功，但在未匹配记录上出现期望 0、实际 1 的反例；改为 `COUNT(order_id)` 后四场景通过。还验证了非法语法、ATTACH 拒绝、真实模型教练、取消、刷新持久化和正式账本不变。详细操作见 [体验手册第 3 节](QueryStep%20本地启动与体验手册.md#3-sql-实作工作台)。

旧正式错题教练的一次 HAVING 真实调用在取得正确课程与实验结果后触及原 8 秒总预算，降级而非丢失证据。外部模型延迟无法由本地测试保证，报告不把每一次真实调用都描述为成功。

### SQL 诊断比较

固定案例位于 `evals/workbench_cases.py`，四臂运行器位于 `evals/workbench.py`。共 100 个 SQL 程序，30 个正确、67 个错误、3 个拒绝案例；按任务划分 60 开发、40 测试，每个冻结标签均以四场景、三个种子复核。本轮 1,200 次场景/种子标签审计全部一致。

四臂为 direct、单次课程 RAG、动态 Agent、无学习上下文 Agent。输入题面和学生 SQL 一致，但调用预算不同，不能称为等成本比较；Agent 的优势也不能仅归因于 LangGraph 而忽略执行工具的贡献。报告保留判定准确率、误指责、有效反例、证据一致性、超时/降级、延迟及实际返回 token；费用未知保持 null。

正确判定口径是“已暴露的有限验证证据”：引用的完整通过检查可在同一种子下合并场景覆盖，任何真实反例优先。它不是形式化 SQL 等价证明。语义标签由作者冻结，执行器只审计、不自动重新标注。

案例由编码助手参与编写，尚未经过独立教师审核；测试任务也用于功能验收，因此仅称为任务不重叠的内部测试，不能称为外部盲测。上下文比较使用明确标记的合成学习快照，不是真实学生研究，也不包含虚构的 EpiKT 推理值。教学质量、学习增益和真实 EpiKT 上下文收益均未测量。

### 2026-11-20 实际四臂结果

冻结的内部测试集包含 40 例：12 个正确查询、28 个错误查询，拒绝案例全部在开发集。模型为 `gemini-3-flash`，使用 hybrid 检索及 `novice-v1` 合成上下文，并发为 2；每个案例运行全部四臂，共 160 次，未剔除失败。以下是第一次完整测试结果，不以之后较好的开发集重测替换。

| 方法 | 正确判定/40 | 误指责/12 个正确查询 | 未判定 | 有效反例/声称反例 | 模型错误/超时/格式失败 | P50 / P95 秒 |
|---|---:|---:|---:|---:|---:|---:|
| direct | 20（50.0%） | 2 | 18 | 3/6 | 16 / 1 / 1 | 1.44 / 3.79 |
| RAG | 21（52.5%） | 1 | 17 | 9/13 | 15 / 2 / 0 | 3.99 / 9.82 |
| Agent | 19（47.5%） | 0 | 21 | 14/14 | 15 / 4 / 1 | 5.75 / 12.17 |
| 无上下文 Agent | 14（35.0%） | 0 | 26 | 12/12 | 16 / 4 / 1 | 5.54 / 12.49 |

降级与未判定并非同义：第二次模型调用超时后，已取得的真实反例仍可支持判定；反之，仅检查部分场景的正常结束仍不足以判定全场景通过。反例有效率以实际声称反例为分母，不意味着覆盖全部错误；Agent 两臂分别覆盖 14/28 与 12/28 个错误案例。每个评估臂冷启动 MCP，因此此处延迟也不是复用连接后的生产 API 热请求延迟。

四臂实际模型请求数分别为 40、40、73、69；返回 token 的请求数分别为 23、23、54、49。已返回的部分 token 合计分别为 25,338、46,274、158,023、133,767，不能当作完整消耗或据此声称节省成本；完整 token 和费用均保持 null。

结论是：执行证据约束减少了本次观测到的误指责，已展示的 Agent 反例全部通过复核，但整体正确率没有优于 direct/RAG，连续模型调用错误及证据覆盖不足明显影响可用性，尚不满足高质量 Agent 的整体验收。之后对原有 12 个开发案例做诊断重放，连续模型错误未复现（四臂正确判定为 9、9、11、9），仍有超时和一次无效计划；这只能说明结果存在波动，不能确认限流、网络或提供方根因，更不能替换测试集结果。

原测试报告 SHA256 为 `88de15ef874134e99b5aa57ed95370bb08fd818f9d52976afa19fef5823f1c5c`，案例集 SHA256 为 `9032de048dacf46e08e4da2047e0682685337cae36262744efd6ab599d58f938`。报告同时保存当时的源代码指纹、预算、检索版本与全部失败。评估之后补充了 HTTP 状态码、传输超时/错误、无效响应的安全诊断记录；不存储异常正文、地址、请求头或密钥，也不增加隐式重试。失败响应若确实返回合法 token 用量仍如实保留。原报告的源码指纹对应补充诊断前的版本，不冒充最新版本重测。

### 2026-11-25 V2 优化与四臂复测

针对 2026-11-20 V1 失败日志中的四类根因完成定向优化（不修改冻结案例与标签）：
1. **紧凑规划协议与场景覆盖提示**（`tutor/workbench_coach.py`，`workbench-plan-v4`）：用紧凑 JSON 协议替代每轮透传的 `Plan.model_json_schema()`（系统提示由 6,637 字节降至 2,677 字节，降幅 59.7%）；明确核对题面时直接调用全场景 `check_student_sql` 而非先 `run_student_sql(sample)`，并在状态中透出确定性 `checked_scenarios` / `unchecked_scenarios`，单次模型超时调整至 10 秒。
2. **显式可选的有界瞬时重试**（`tutor/provider.py`、`api/main.py`）：默认 `max_retries=0` 保持原有无隐式重试契约；评估与服务端可显式开启对 HTTP `429/502/503/504` 与连接中断的短退避重试（受调用超时约束，每次真实请求均透明计入 `measure_calls()`）。
3. **热 MCP 评估口径**（`evals/workbench.py`）：新增 `--mcp-mode warm` 与 `--transient-retries`，对齐生产 API 复用常驻 MCP 进程的行为，并在报告中显式标注冷/热启动口径与重试参数。

在相同 40 例冻结内部测试集（案例集 SHA256 仍为 `9032de048dacf46e08e4da2047e0682685337cae36262744efd6ab599d58f938`）、`novice-v1` 合成上下文、hybrid 检索、并发为 2、热 MCP 与 `--transient-retries 2` 条件下运行 V2 评估。因当日上游代理中 `gemini-3-flash` 持续返回 HTTP 503，本次四臂统一使用当时可用且稳定返回完整 token 的 `gpt-6-sol`（报告 `artifacts/workbench-test-v2-gpt6sol.json`，SHA256 `c85de98d21205c2f385681ee72298d5eeb236880acefb9be3ade0d1a45834d05`）；跨模型不可直接等同于同模型消融，待 `gemini-3-flash` 恢复后可用同一命令补跑同模型复测。

|---|---:|---:|---:|---:|---:|---:|---:|
| direct | 40（100.0%） | 0 | 16/28（57.1%） | 0/28 | 0 / 0 / 0 | 42,459（40/40） | 3.41 / 3.94 |
| RAG | 40（100.0%） | 0 | 17/28（60.7%） | 0/28 | 0 / 0 / 0 | 81,662（40/40） | 4.30 / 5.57 |
| Agent | 39（97.5%） | 0 | **28/28（100.0%）** | **28/28** | 0 / 0 / 1 | 135,062（79/79） | 6.18 / 8.16 |
| 无上下文 Agent | 40（100.0%） | 0 | **28/28（100.0%）** | **28/28** | 0 / 1 / 0 | 120,208（79/80，partial） | 5.98 / 7.67 |

观察结论：
- **规划效率与 Token**：全部 79 次完成的 Agent 运行均在 1 次全场景 `check_student_sql` + 2 次模型调用内收敛，V1 中 `run_student_sql(sample)` 导致的漏检与多余轮次降为 0；Agent 单次模型调用均值由 V1 的 ~2,926 tokens 降至 1,710 tokens（降幅约 42%），总 Token 与 Direct 之比由 6.24× 降至 3.18×（仅为 RAG 的 1.65×）。
- **工具沙箱的核心增量**：即便在强模型使 Direct/RAG 二分类达到 40/40 时，Direct/RAG 仍有约 40% 的错题无法给出有效反例且完整可执行反例载荷为 0/28；Agent 两臂均实现 **28/28（100%）** 完整可执行反例与 100% 证据一致性。
- **剩余边界**：Agent 仍有 1 例首轮 `invalid_plan`（`order_top.03`），无上下文 Agent 有 1 例第二轮超时但保留了首轮反例证据仍正确判定；独立教师审核、同模型（`gemini-3-flash`）V2 复测与真人学习增益仍待后续开展。

### 本地工作台交付验证

本地服务加载了新版知识库的 26 张卡片。真实浏览器在隔离会话中复现零订单客户被 `COUNT(*)` 计为 1 的反例，改用 `COUNT(order_id)` 后通过 4 组数据验证。Gemini 调用 SQL 检查工具并完成提示。另一轮经 MCP 混合检索命中 `count/sum-null`，刷新后仍可在执行轨迹中核对课程指纹 `af0601a9eb13`。正式答题进度在测试前后保持一致。Python 回归 324 项通过，前端生产构建通过。

初测中，Gemini 将中文的 `SUM` 问题改写为 `SUM NULL empty table`，通用的 `NULL` 卡片挤占了前三条结果。调整混合排序，在已满足检索条件的卡片中优先展示标题或审核关键词匹配的明确 SQL 运算项，保留其余候选的原有排序。复测中也观察到上游 Gemini 返回 HTTP 503，浏览器正确显示降级状态。默认模型恢复后，真实工具调用和课程检索均通过浏览器复测。完整四臂重测、独立教师复核和真人试用待后续开展。
